Codebase Context

The app uses App Router, TanStack Query, and local Go route handlers. The previous performance plan already addressed several common issues, including cancellable ledger queries and intent-driven prefetching. This review prioritized observable behavior, concrete request sequences, and component design that makes regressions harder to introduce.

ESLint and TypeScript passed. The web-platform legacy scanner reported zero matches across 96 files and 52 rules, covering roughly 20% of its guidance corpus. The review used static source inspection and did not measure timings or run browser reproductions.

I1. Keep import results tied to the submitted draft

Mutation state · 98% confidence · Medium complexity

A late file.text() completion can overwrite newer input and advance the wizard. While import is pending, the user can change accounts or steps. Success then clears current input and the receipt reads the current account.

Track the latest input intent, surface read failures, and capture immutable submission variables for the success receipt. Decide which pending transitions should remain available, since locking every control can make a long import feel stuck.

Source evidence at submission and success, file reads, and receipt and account controls.

I2. Refresh account balances and category and tag counts after import

Cache consistency · 98% confidence · Low complexity

The import attaches transactions to accounts, categories, and tags. Its success handler refreshes the ledger and spending queries only. Recently cached balances and transaction counts can therefore reappear stale when the user navigates to those views.

Reuse the transaction invalidation helper, or narrow it to the affected query keys if a trace shows avoidable fetches. The existing helper invalidates broad query families, which can cause extra requests for mounted consumers.

Source evidence at import success, import writes, and the shared invalidation helper.

I3. Filter card-payment candidates before pagination

Data flow · 97% confidence · Medium complexity

The transfer picker requests a page of all transfers, then removes rows whose destination is outside the credit-card accounts. It can show an empty page even when eligible matches exist, and the pager reflects the count of all transfers.

Put eligibility into the query that returns rows and counts. This takes a Go and TypeScript query-contract change and needs coverage for mixed transfer history.

Source evidence at the transfer picker.

I4. Use one source of truth for the Settings tab

Route state · 95% confidence · Low complexity

The page passes URL parameters to a component that consumes them only in a state initializer. Same-route URL changes can retain the mounted tab state. Each tab click also uses router.replace for a client-side display choice.

Use the established URL-state pattern from Categories & Tags. Preserve Gmail callback defaults and feedback while checking direct links and browser navigation.

Source evidence at the route, the client tab state, and the existing pattern. See Next.js navigation guidance.

I5. Start inspector data and code loading together

Loading · 96% confidence in the request sequence · Low complexity

The first drawer open downloads the dynamic component, then starts the detail query after mount. Start the canonical detail query when the user opens a transaction so code and data can load together. Retain lazy loading and measure a cold drawer open. Each abandoned open can still issue a detail request.

Source evidence at the dynamic boundary, the open handler, and the detail query. See Next.js lazy-loading guidance.

I6. Parse each import draft once

Render work · 99% confidence in repeated work · Medium complexity

The controlled input parses and normalizes all rows for each text edit. A file upload parses in the handler and the render path parses the same payload again. useMemo still recomputes for each edit because the input changes.

Share one parse result per committed input. Decide when to validate based on whether users need live feedback or can validate at Preview. Profile a representative large import before introducing workers or paginating the preview.

Source evidence at render-time parsing, upload parsing, and the parser. See React memoization guidance.

I7. Isolate transaction patch construction

Component design · 90% confidence · Low complexity

The inspector form builds its update payload inline alongside draft guards, mutations, and UI. The patch rules combine currency changes, timezone conversion, and omitted or cleared fields. A pure transaction patch function would make those cases independently testable. Keep it close to the inspector unless another caller needs the same rules.

Source evidence at the submit flow and the prior form design learning.

Ideas Set Aside

  • Fetch Go handlers from Server Components across the app. Installed Next.js guidance describes the build-time listener limitation and runtime round trip. Keep the existing same-origin client path unless a supported direct data path earns its cost.
  • Replace TanStack Query with SWR or wrap independent query hooks in Promise.all. The hooks already run in parallel and share cache entries.
  • Remove effects or add memoization broadly. Existing effects handle lifecycle cleanup and URL synchronization. Memoization would need a measured render bottleneck.
  • Move every dialog behind a new dynamic boundary or prefetch every row. Several heavy paths already load on demand. Blanket prefetch would multiply detail requests.
  • Replace the full Lucide dynamic icon path. The broad registry is present, but delivered bundle cost and icon paint need measurement. Keep persisted custom icon names in any later experiment.
  • Split the inspector by file size. Extracting the patch rules gives a specific testability benefit without moving draft and focus ownership.
